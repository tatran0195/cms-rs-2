# Nibleaf → cms-rs Porting Gap Analysis

**Scope:** verify that every feature and endpoint of the original **nibleaf** Node.js monorepo
(`lord007tn/nibleaf`) has been correctly ported to the **cms-rs** Rust + Vite-SPA stack
(`tatran0195/cms-rs`).

**Date:** 2026-09-04
**Method:** static analysis of both codebases (routers, handlers, frontend RPC call sites, auth
client, site server). Endpoint coverage was generated by extracting every frontend API call and
cross-referencing the Rust router table; implementation status was classified by inspecting each
handler body (real DB/service call vs. hardcoded `{ "data": … }` no-op).

## 0a. Product-flow and public-serving verification (2026-10-02)

This current-status addendum supersedes statements below that are explicitly dated 2026-09-04 or
still describe the pre-hardening implementation. The first report was a static route/handler audit;
this follow-up also ran the PostgreSQL-backed product flow and exercised the actual host SSR router.

### Verified since the historical audit

- **Real release snapshots are the public source of truth.** The public API resolves a successful
  release snapshot (default branch unless a version is explicitly selected), and the custom-host
  SSR path now does the same. SSR checks the live `Project.is_public` flag so access can be revoked
  immediately, but renders the project's metadata and pages from the selected immutable snapshot.
  It no longer reads mutable `Page` rows through `PageQueries::get_by_project`.
- **SSR scope is explicit:** public subdomains select the latest active default-branch release;
  custom domains use the active snapshot bound to their deployment. The snapshot's enabled default
  language determines the page index, `<html lang>` and text direction. SSR matches the exact
  release/language/path and only serves published `PAGE` records. A feature branch does not become
  the default site merely because it was deployed more recently; if there is no active default
  release, the default host returns 404. A custom domain whose bound deployment has no active
  snapshot also returns 404 rather than silently falling back.
- **Single-page SSR is bounded.** It fetches one page body through the indexed
  `(deployment_id, language_id, path)` snapshot lookup. SEO canonical URLs and the XML sitemap now
  preserve the complete nested page path and use the actual custom/subdomain site root. JSON-LD is
  serialized as valid JSON and protected against `</script>` injection; user-controlled listing
  metadata is HTML-escaped. Robots, manifest, sitemap and rendered pages all use release metadata.
- **Branch merge now completes a real publish.** `POST /app/projects/:id/branches/:id/merge` invokes
  the same snapshot capture/render/publish pipeline and returns a ready release instead of only
  leaving an unqueued `BUILDING` deployment behind.
- **New-language document creation and translation coverage are exercised.** The E2E creates an
  `ar-EG` language and Arabic group/page, verifies persisted language IDs, rejects a parent from a
  different language/project, and proves Arabic/English content remains isolated. Coverage uses the
  existing scoped `PageQueries` list API, counts `PAGE`-kind records on the default branch (including
  drafts as editor records), and matches translations by identical path; groups are excluded. The
  unit/E2E assertions include missing, extra and draft pages.
- **Custom-domain ownership is DNS-proven.** Verification checks that the submitted token matches
  the persisted challenge, queries `_cms-rs-verification.<hostname>` through the configured HTTPS
  DNS JSON resolver, requires an exact TXT answer with a successful DNS status, and only then writes
  `verified_at`; an explicit failed re-check revokes the routing grant. Unit tests cover exact-answer,
  wrong-token and NXDOMAIN cases. The E2E still manually marks its `.invalid` fixture verified rather
  than depending on public DNS propagation.
- **Domain mutations now reach the canonical lifecycle queries.** The authenticated top-level
  `PUT /api/domains/{id}` uses the hostname-aware atomic update, so hostname changes rotate the
  challenge and clear verification/TLS state while unrelated partial updates preserve it. Domain
  creation normalizes IDNA/case/trailing dots, and primary-domain create/promote operations serialize
  on the deployment row and update atomically. E2E exercises partial-update preservation, rename
  invalidation, and cache-safe old-host rejection through the real API.
- **Host resolution caching is now persistent, bounded and invalidatable.** `cms-sites` builds one
  resolver per router instead of constructing one per request. It caches positive and negative
  results for up to 30 seconds, caps the map at 4,096 hosts, tags entries with a shared generation,
  and API domain mutations bump that generation so ownership/hostname changes invalidate immediately.
  Out-of-band database changes remain bounded by the 30-second TTL.
- **Legacy snapshot migration was simulated transactionally:** pre-migration page bodies were
  backfilled into `DeploymentSnapshotPageIndex` and removed from snapshot metadata.
- **Root fallback listings and sitemaps are body-free.** Snapshot creation now copies title, slug,
  parent, published state, kind, and page update time into the page index; a new migration backfills
  these fields and adds a partial covering index for published PAGE listings. Root serving queries
  that compact metadata first, fetches a body only for the selected root page, and renders the
  fallback listing without body JSON. Sitemap generation uses the same metadata-only query. The
  PostgreSQL E2E asserts the listing metadata, the root listing's page title, and absence of the
  document Markdown body from the fallback HTML.

### End-to-end evidence

PostgreSQL 17 was installed and running locally; `cms_e2e` is a disposable test database. These
commands passed:

run separately by `cargo xtask e2e` (1/1 passed against the disposable PostgreSQL 17 `cms_e2e`
database); `_sqlx_migrations` confirms migration `20260112000000` completed successfully. The E2E
drives project/language/page creation, publication,
language artifacts, public API and host SSR, an unpublished draft, live edits/renames remaining
invisible until release 2, a feature-branch publish explicitly selectable by version but not by the
default host, rollback to release 1 as release 3, and the missing-default-release 404 edge case. It

### Remaining production risks / bottlenecks (not claimed fixed)

1. **Two rendering models still coexist:** the app host can serve the frontend SPA while custom
   hosts use Rust SSR. The product must settle whether the SPA client site or Rust SSR is canonical,
   especially for parity in MDX/custom components.
2. **SSR only serves the release's default language and default branch on ordinary subdomains.**
   The public API can select other languages/branches; host-SSR language/version negotiation remains
   unimplemented.
3. **DNS verification has unit but not live-DNS E2E coverage.** The E2E fixture uses a reserved
   `.invalid` hostname and manually verifies it, so resolver timeout, propagation, and authoritative
   TXT behavior still need a controlled DNS integration test. Certificate issuance/renewal is
   delegated to the configured Caddy edge and is not exercised by this E2E.
4. **Out-of-band database mutations may leave host mappings cached for up to 30 seconds.** Supported
   domain API mutations invalidate immediately through the shared generation counter; operational
   scripts and any future direct-write jobs must explicitly invalidate or account for the bounded TTL.
5. **Deployment processing is synchronous in HTTP handlers.** Large projects may exceed the
   configured request timeout; cancellation after the deployment is claimed can leave it stuck in
   `BUILDING`. A durable queue/worker acknowledgment model and load/failure tests are still needed.

## 1. Historical TL;DR — baseline findings from 2026-09-04

> This section's endpoint counts and findings describe the original pre-fix static audit only. They
> are not current status; use §0a for the latest product-flow test results and remaining risks.

**At the time of the original audit, the URL/routing surface was ported almost perfectly, but most
of the business logic was a stub.**

The Rust `cms-api` router preserves the original path structure (the frontend's RPC proxy resolves
~115 of 116 calls to a registered route), **however the majority of those routes are serviced by
placeholder handlers that return hardcoded values** (`{ "data": { "success": true } }`,
`{ "data": [] }`, `{ "data": null }`, `{ "text": "Draft content" }`) and ignore their inputs.

Quantified, for the endpoints the SPA actually calls:

| Status | Count | Meaning |
|--------|------:|---------|
| ✅ Real implementation | **41** | Queries the DB / runs real logic |
| ⚠️ Hollow stub / no-op | **74** | Route exists, returns hardcoded placeholder |
| ❌ Route missing | **1** | `GET /api/public/pages/{id}` (an orphan call in cms-rs' own frontend) |
| **Total** | **116** | |

A secondary, related problem: several **real** implementations were ported into *top-level* routers
(`/api/comments`, `/api/branches`, `/api/pages`, `/api/search`, `/api/export`, …), but the frontend
is wired to the *project-nested* routes (`/api/app/projects/{projectId}/comments` …), which are the
**stub** handlers. So features can look implemented in the code but silently no-op at runtime.

The practical result is a dashboard that **loads a few things but cannot actually create/connect/export
anything**, plus a docs-site renderer where **search, AI answers, changelog and analytics are
disabled** (they return empty/hardcoded responses).

## 2. How the two systems map

### nibleaf (Node, original)
- `apps/server` — Hono API under `/api`. Modules: `app/*`, `public/*`, `admin`. Auth is **Better Auth**
  mounted at `/api/auth/*`. Site rendering is SSR (TanStack Start) via `apps/app`, with a separate
  Cloudflare edge worker (`apps/custom-domain-edge`) for custom hosts.
- `apps/app` — TanStack Start frontend (dashboard + editor + **also serves the published docs site**
  at `sites/$projectId/...` + marketing pages). Calls the API through a typed Hono RPC client
  (`api.app.projects[':projectId'].pages.$get()`).
- `apps/admin` — separate admin console.
- `apps/worker` — background workers (deploy, search index, exports).
- `packages/*` — database (Prisma), auth, storage, search, analytics, i18n, validators, design-system.

### cms-rs (Rust + SPA, target)
- **Rust workspace** with layering: `cms-api` (Axum routers/handlers) → `cms-biz` (services) →
  `cms-db` (SQLx), plus `cms-entity`, `cms-auth`, `cms-authz`, `cms-storage`, `cms-search`,
  `cms-queue`, `cms-analytics`, `cms-mcp`, `cms-sites`, `cms-middleware`, `cms-worker`.
- `src/main.rs` (composition root) mounts: `Router /api (api_router)` merged with `cms-sites`
  (`sites_router`), with config-driven CORS (fixed this batch), compression, timeout, tracing layers.
- `frontend/` — **a near-verbatim copy of nibleaf's `apps/app`**, but running on **TanStack Router +
  Vite** (no server, no proxy) and already rendered as an SPA.

**Architecture intent (per user):** the SPA is served directly by the Rust server (no Node proxy);
custom-host resolution is also done by Rust (`cms-sites::host_resolution`). This replaces nibleaf's
Node SSR + Cloudflare edge.

## 5. Auth flow — substantial gaps & a security hole

The SPA uses a native **Better Auth** client (`@cms/auth/client` → `createAuthClient` with
`basePath: '/api/auth'`, plugins `emailOTPClient`, `organizationClient`, `adminClient`). The Rust
server implements a *custom* auth router at `/api/auth` with a small subset of Better Auth's URLs.

| Frontend call | Better Auth path | Rust handler | Status |
|---|---|---|---|
| `signIn.emailOtp({email,otp})` | `POST /auth/sign-in/email-otp` | `sign_in_email_otp_handler` | ✅ **Fixed** — validates a matching, unexpired, single-use code; rejects invalid/expired; no blind auto-create |
| `emailOtp.sendVerificationOtp({email})` | `POST /auth/email-otp/send-verification-otp` | `send_verification_otp_handler` | ✅ **Fixed** — issues a 6-digit code (10-min TTL) stored in `VerificationToken`, logged for dev; no response echo |
| `useSession` | `GET /auth/get-session` | `get_session_handler` | ✅ |
| `signOut` | `POST /auth/sign-out` | `sign_out_better_auth_handler` | ✅ |
| `signIn.social({provider:'google'})` | `POST /auth/sign-in/social` | `sign_in_social_handler` | ✅ **Done** — returns the configured provider's authorize URL (embedding the SPA callback URL in the OAuth `state`). | `signUp.email` | `POST /auth/sign-up/email` | — | ℹ️ Not needed — the SPA sign-up page uses the email-OTP flow, not password sign-up (there is no `password_hash` column). |

**Remaining auth issues:**
1. **Security: FIXED.** The OTP bypass (any-OTP sign-in + no delivery) has been closed; `sign-in/email-otp`
   now requires a matching, unexpired, single-use code. Remaining concern: OTP delivery is logged for
   dev/self-host rather than emailed unless a real `Mailer` is wired — acceptable for dev, but production
   must send the code to the inbox.
2. **Cookie name:** aligned. The whole auth surface (email-OTP sign-in, OAuth, `get-session`,
   logout, and the `AuthExtractor` middleware) now uses Better Auth's default
   `better-auth.session_token`. The CSRF/refresh handshake remains simplified (the SPA runs
   same-origin with `credentials: include`).
3. **Password sign-in** is not wired to the Better Auth `/auth/sign-up/email` / password endpoints
   (there is no `password_hash` column); the SPA uses email-OTP instead. **Social OAuth is now
   functional end-to-end** — `POST /auth/sign-in/social` returns the provider authorize URL, and
   `GET /auth/callback/:provider` exchanges the code, upserts the user/account, creates a session,
   sets the cookie, and redirects back to the SPA.

## 6. Published “app site” (docs site) — the other main problem

There are two competing render paths, which is exactly the ambiguity the user flagged:

1. **`cms-sites` (Rust SSR)** — `sites_router` resolves the `Host` header to a project
   (`host_resolution.rs`), then renders page HTML from the selected immutable active-release
   snapshot (Markdown → sanitized HTML via `pulldown-cmark`/`ammonia`). Custom domains use the
   snapshot bound to the domain deployment; ordinary subdomains use the default-branch release.
   Mutable editor page rows are not a public rendering source.
2. **SPA route `sites/$projectId/…`** — the copied TanStack router still has docs-site routes that
   fetch `/api/public/sites/:id`, `/sites/:id/page`, etc. and render client-side.

For the "serve SPA directly + resolve custom host in Rust" model, the docs site should be served as
**either** the SPA (client-side) **or** the Rust SSR — not both. Right now a custom host gets Rust SSR
while `app.cms.app` (no host mapping) gets the SPA, and the SPA routes also try to build the site.

Remaining defects in the public API the SPA uses (`crates/cms-api/src/public/handlers.rs`) are now
fixed:

- `search_public_site_handler` → **FIXED** (runs `SearchService::search` and maps hits).
- `answer_public_site_handler` → **FIXED** (runs `SearchService::get_rag_answer` and returns the answer + source pages + confidence).
- `get_public_site_changelog_handler` → **FIXED** (returns the real Deployment rows as release entries).
- `post_public_site_events_handler` → **FIXED** (records a real analytics event via `AnalyticsService::record_event`).
- `get_public_domains_resolve_handler` → **FIXED** (resolves the host via the Domain → Deployment chain).
- `get_public_invitation_handler` → **FIXED** (looks up the real `Invitation` row by token and returns org name, email, role, expiry).
- `get_public_meta_handler` → **FIXED** (reports which OAuth providers are actually configured).
- `get_public_git_preview_handler` → **FIXED** (resolves a preview deployment by id).
- **`GET /public/pages/{id}`** → **added** (was the single missing route); returns the real published page.

**Machine/document endpoints added** (previously absent from the public router; now all real):
- `GET /public/sites/:id/markdown` → concatenated Markdown of all pages.
- `GET /public/sites/:id/openapi.json` → the project's stored OpenAPI document.
- `GET /public/sites/:id/changelog/rss.xml` → RSS feed from the real Deployment rows.
- `GET /public/sites/:id/sitemap.xml` → XML sitemap of the site's pages.
- `GET /public/sites/:id/robots.txt` → robots.txt + Sitemap directive.
- `GET /public/sites/:id/llms.txt` → concise page index for LLMs.
- `GET /public/sites/:id/llms-full.txt` → full concatenated page content.

**TOC + pagination fixed:** `get_public_site_handler` and `get_public_pages_handler` now emit a real
`headings` array (parsed from the page's Markdown) and `prev`/`next` navigation computed from the
project's ordered pages.

**Current snapshot contract:** the stale pre-hardening claim that the public nav lists every mutable
project page is no longer accurate. `resolve_public_site` now selects one active release branch and
one enabled language, reads its immutable page index, returns hierarchical navigation for that
scope, and enumerates the latest published release on each branch in `versions`. `lang` selects a
language; `version` selects a branch slug/ID (the latest successful snapshot on that branch). The
page payload also contains parsed headings and computed previous/next navigation.

**Machine/document route note:** the listed `/api/public/sites/:id/markdown`, `/openapi.json`,
`/changelog/rss.xml`, `/sitemap.xml`, `/robots.txt`, `/llms.txt`, and `/llms-full.txt` endpoints were
added by the earlier porting batches. The separate `cms-sites` router serves top-level sitemap and
robots files for resolved hosts. Do not treat these route families as missing; the remaining parity
question is whether all representations use the same immutable release and host/language policy.

**MDX compatibility:** the nibleaf content model is **MDX** (callouts, custom components, mermaid,
katex, code blocks). `cms-sites::markdown_renderer` uses `pulldown-cmark` (standard Markdown) with a
post-processing pass that now handles the editor's canonical MDX callouts. GitHub admonition
blockquotes (`> [!NOTE]`, `> [!TIP]`, …) render as `div[data-callout][data-variant]`, and ` ```mermaid`
fenced blocks are preserved as `<pre class="mermaid">` for client-side hydration. Remaining MDX
constructs (custom components like `<Tabs>`, `<Accordion>`, KaTeX math) are not yet rendered by the
SSR path — these are best handled in the SPA, which already compiles MDX via `mdx-components.tsx`.

## 7. Custom-domain / host resolution & serving concerns

- `cms-sites::host_resolution::HostResolver` resolves the `Host` header against the DB. It is
  constructed once per router with the config-derived base host from `site_host()` (`site.self_host`
  → `site.marketing_host` → fallback `"cms.app"`), so self-hosted operators / branded deployments
  no longer need `cms.app` baked in. Subdomain detection also matches the configured base host in
  addition to the legacy `cms.app`/`cms.com`/`cms.dev` suffixes. The shared cache is bounded to 4,096
  hosts with a 30-second TTL and a generation counter; successful domain API mutations invalidate
  positive and negative entries immediately. Out-of-band DB writes remain bounded by the TTL. Custom
  domains require DNS-proven `verified_at` (see §0a); live DNS and certificate lifecycle still need
  integration coverage.
- The SPA fallback (`serve_spa_file`) checks a few candidate dirs (`dist/frontend`, `frontend/dist`,
  `../dist/frontend`, `../frontend/dist`). Confirm the build output path matches what ships, or the
  SPA will render the "Frontend assets not found" fallback HTML.
- CORS is now config-driven (`build_cors` in `main.rs`) and permits credentialed cross-origin requests
  only for origins in `[admin_origin]` (+ localhost in dev). (Fixed this batch.)
- `.layer(TimeoutLayer::with_status_code(REQUEST_TIMEOUT, 30s))` will time out long exports/builds.
- The wildcard catch-all `/{*path}` in `sites_router` coexists with explicit `/assets/…`, `/css/…`,
  `/js/…`, `/images/…`, favicons, manifest, `/robots.txt`, `/sitemap.xml` — axum prioritizes the more
  specific route, but it's worth a quick smoke test that `/api/*`, `/assets/*`, and SPA route
  deep-links (`/projects/:id/editor`, `/sign-in`) all resolve correctly.
- `main.rs` still enables `mcp.enabled=false` by default (operator choice). `AppError` now emits the
  frontend's `{ error: { code, message, details } }` envelope; `client-helpers` reads
  `body.error.message` / `body.error.details.errors[0]`.
